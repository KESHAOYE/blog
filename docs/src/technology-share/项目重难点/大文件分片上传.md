# 大文件分片上传

大文件上传的普遍方案是文件分片上传

如果把文件上传看做是一个不可分割的事务，那么分片的目标就是把一个好事的大事务划分为一个一个小事务。

由于公司使用BFF层来承接前端的文件请求，因此需要大同前后端所有跟文件上传的障碍

## 主要障碍

- 如何减少页面阻塞
- 前后端如何协调
- 代码如何组织
- 前端代码中的复杂逻辑
- BFF代码中的复杂逻辑

### 如何减少页面阻塞

分片上传的首要目标就是尽量避免相同的分片重复上传。服务器必须要能够识别来自各个客户端的各个上传请求中，是否存在与过去分片相同的上传请求。

#### 如何识别分片是相同的？

文件内容一样即为相同；可是对文件进行二进制对比是一个十分耗时的操作，于是可以选择基于内容的hash来进行对比

> hash是一种算法，可以将任何长度的数据转换为定长的数据库，常见的hash算法有MD5。
> 本项目使用MD5进行hash计算，使用的是第三方库Spark-MD5。

流程：前端先计算分片，将hash上传服务器进行校验，如果存在对应分片则不上传，不存在则继续上传。根据所有分片的hash值可以计算出整个文件的hash值。（先发送整体hash校验服务器上是否有相同文件！）

**计算hash是一个CPU密集型任务，不加处理就会导致长时间阻塞主线程**

#### 如何解决？

**方案**：假设绝大部分的文件上传都是新文件上传。即不需要等待所有分片计算完成，当第一个分片计算完成的时候就开始上传。（这时候如果之前上传过该分片会直接跳过）

##### 对比

这样做的好处是，页面完全无阻塞，也无需等待整体hash即可启动上传，相较于传统方案：

- 对于新文件可以缩短整体上传时间，消除页面阻塞
- 对于旧文件上传可能会产生一些无效请求，但这些请求仅传递hash，并不真实上传文件数据，对网络和服务器的影响都很小，加上旧文件重复上传情况相对较少，所以整体影响可以忽略不计。

### 前后端怎么协调？

文件上传涉及到前后端的交互，需要建立一个标准的通信协议，通过协议要能完成下面几件核心交互：

- 创建文件
- hash校验
- 分片数据上传
- 分片合并

#### 创建文件协议

当客户端发送分片到服务器时，需要告知服务器分片属于那一次文件上传，因此需要一个唯一标识来表示某一次文件上传

创建文件协议就是用于获取文件上传的唯一标识

通过HEAD请求（只有请求头和响应头），带上文件大小、文件名、文件MIME类型，后端返回chunkSize（分片大小）、uploadToken（文件上传的唯一标识）

#### hash校验协议

客户端有时需要校验单个分片或整个文件的hash，服务器需要告知客户端目前的具体情况。

有两种情况：

- 上传单个分片hash值：还是使用HEAD请求，带上token、hash-type（chunk，代表是分片hash），hash，后端返回是否存在这个分片
- 整个文件的hash值：和单个分片类似，只不过上传的hash是整个文件的hash，上传的hash-type是file（代表整个文件），后端返回是否存在这个文件和需要的分片（指示还剩余哪些hash没有上传），如果存在这个文件还要返回这个文件的url

#### 分片上传协议

这部分就是文件上传，不过在请求头上需要带上upload-token、upload-chunk-index、upload-hash。

文件上传的content-type有三种，分别是application/json、mutipart/form-data（需要使用FormData构造器）、application/octet-stream（请求体类型为文件二进制数据）

#### 分片合并协议

通过HEAD请求，带上token和Upload-Operation：Merge字段，后端会返回url

##### EventEmitter类 - 发布订阅模式

```js
export class EventEmitter<T extends string> {
    private events: Map<T, Set<Function>>;
    constructor() {
        this.events = new Map();
    }

    on(event: T, callback: Function) {
        if (!this.events.has(event)) {
            this.events.set(event, new Set());
        }
        this.events.get(event).add(callback);
    }

    off(event: T, callback: Function) {
        if (this.events.has(event)) {
            return
        }
        this.events.get(event).delete(callback);
    }

    once(event: T, callback: Function) {
        const onceCallback = (...args: any[]) => {
            callback(...args);
            this.off(event, onceCallback);
        }
        this.on(event, onceCallback);
    }

    emit(event: T, ...args: any[]) {
      if(!this.events.has(event)){
        return
      }
      this.events.get(event).forEach(callback => callback(...args));
    }
}
```

##### TaskQuene类

为支撑前后端的多任务并发执行，提供TaskQuene类

> 前端可能的并发任务：并发请求
> 后端可能的并发任务：并发的分片校验

export class Task {
  fn: Function;
  payload?: any;
  constructor(fn: Function, payload?: any) {
    this.fn = fn;
    this.payload = payload;
  }
  run() {
    return this.fn(this.payload);

#### 如何分片？

```js
  export interface Chunk {
    blob: Blob;
    start: number;
    end: number;
    hash: string;
    index: number; // 分片在文件中的索引
  }

  // 创建一个不带hash的分片
  export function createChunks(file: File, index:number, chunkSize: number): Chunk {
    const start = index * chunkSize;
    const end = Math.min((index + 1) * chunkSize ,file.size);
    const blob = file.slice(start, end);
    return {
        blob,
        start,
        end,
        index,
        hash: ''
    }
  }

  // 计算chunk的hash值
  export function calculateHash(chunk: Chunk): Promise<string> {
    return new Promise((resolve, reject) => {
        const spark = new SparkMD5.ArrayBuffer();
        const reader = new FileReader();
        reader.onload = (e) => {
            spark.append(e.target.result as ArrayBuffer);
            resolve(spark.end());
        }
        reader.readAsArrayBuffer(chunk.blob);
    })
  }
```

接下来，要对整个文件进行分片，分片的方式有很多种，比如：

- 普通分片
- 基于多线程的分片
- 基于主线程时间切片的分片（类似React Fiber）
- 其他分片模式

考虑到通用性，必须要向上层提供不同的分片模式，同时，还要能支持上层自定义一个分片模式。因此，在设计上，使用基于抽象类的模板模式实现。

```js
  // chunks: 产生一部分分片
  // wholehash: 整个文件的hash值都计算完成了
  // drain: 所有分片都处理完成了
  export type ChunkSplitorEvents = 'chunks' | 'wholehash' | 'drain';

  export abstract class ChunkSplitor extends EventEmitter<ChunkSplitorEvents> {
    protected chunkSize: number; // 分片大小
    protected file: File; // 待分片的文件
    protected hash: string; // 整个文件的hash值
    protected chunks: Chunk[] = []; // 分片列表
    private handleChunkCount:number = 0; // 已处理的分片数量
    private spark = new SparkMD5(); // 用于计算hash
    private hasSplited: boolean = false; // 是否已经分片
    constructor(file: File, chunkSize: number = 1024 * 1024 * 5) {
        super();
        this.file = file;
        this.chunkSize = chunkSize;
        // 获取分片数组
        const chunkCount = Math.ceil(this.file.size / this.chunkSize);
        this.chunks = new Array(chunkCount).fill(0)
    }

    split() {
        if(this.hasSplited) {
            return
        }
        this.hasSplited = true;
        const chunkHandle = (chunks: Chunk[]) => {
            this.emit('chunks', chunks);
            chunks.forEach(chunk => {
                this.spark.append(chunk.hash);
            })
            this.handelleChunkCount += chunks.length;
            if(this.handleChunkCount === this.chunks.length) {
                // 计算完成
                emitter.off('chunks', chunkHandle)
                this.emit('wholehash', this.spark.end())
                this.spark.destroy();
                this.emit('drain');
            }
        }
        emitter.on('chunks', chunkHandle)
        this.calcHash(this.chunk, emitter)
    }

    // 计算每一个分片
    abstract calcHash(chunk: Chunk, emitter: EventEmitter<'chunk'>): Promise<void>;

    abstract dispose(): void;
  }
```

#### 如何控制请求？

这部分涉及两个问题：
1、 如何充分利用带宽：分片设计到大量的请求发送，这些请求既不能一起发送造成网络堵塞，也不能依次发送浪费带宽资源，因此需要有请求并发控制的机制；方案：利用基础库的taskQuene实现并发控制
2、 如何与上层请求库解耦：考虑到通用性，上层应用可能会使用各种请求库来发送请求，因此前端SDK不绑定任何请求库。方案：这里使用策略模式对请求库解耦
